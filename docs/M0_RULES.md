# 软件项目状态与资源约束：初始规则表

## R1 必需资源不可用（IR 0.1 已启用）

在同一个项目上下文和同一个有效日期，若正向断言 A 声明任务 T 需要资源 R，正向断言 B 声明同一个 R 不可用，则为“T 阻塞”增加一条正向推导证据。结果保留 A、B 的 ID 和来源。缺省日期只与缺省日期匹配。“需要”表示必需资源，可替换或仅推荐的资源不能按此关系录入。

| 输入变化 | 查询“T 阻塞”的期望（无其他直接证据时） |
|---|---|
| A、B 正向，资源和分区都相同 | 支持，证据含规则名和两条前提 |
| B 缺失、只有反向 B，或以站会因果报告替代 B | 未知 |
| B 属于另一资源、日期或上下文 | 未知 |
| A、B 均正向，同时有直接证据否定结论 | 冲突 |
| B 自身有正反两条证据 | 0.1 仍触发 R1。这是已知限制 D1。P-3 要决定冲突前提应如何处理 |

## 候选规则（待语义评审）

下列中文关系名供建模讨论。每条候选先固定概念 ID、显式角色和输出分区，再写一对正例与反例。各行反例均假设没有其他支持证据。

| 候选 | 同分区内的充分条件和结论 | 必须返回未知的反例 |
|---|---|---|
| R2 前置验收 | T 启动必须通过指定验收 G，且 G 明确未通过 → T 的该启动条件未满足 | 仅缺少 G 的验收记录 |
| R3 最低容量 | T 对 R 的最低容量为 N，R 可供 T 使用的容量为 M，单位和统计口径相同且 M < N → 该容量条件未满足 | 仅知道 R 总容量，或单位不同 |
| R4 替换资源 | T 明确允许使用 R 的替代项 S，且 S 已获授权并可用 → S 是 T 的可用候选资源 | 仅有 S 与 R 功能相似的描述 |
| R5 显式解除 | 同一阻塞项 B 有授权人签发且已生效的解除记录 → B 的解除有依据 | 单个阻塞项解除时，整项任务是否可发布仍未知 |

R3 依赖量值和单位契约；R5 依赖生效时间和角色契约。候选在引擎中均未注册。新增规则的 PR 需附前提极性、共享变量、分区、来源、推导 ID 及冲突前提的判例，由 Codex 验证执行结果、Claude 复核中文语义。
