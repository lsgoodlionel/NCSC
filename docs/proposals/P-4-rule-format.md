# P-4 规则格式与求值语义

状态：提议 · 关联 #5（M2 规则引擎，Codex 主责）· 新增，不改变 IR 0.2 数据格式

## 问题

0.1 唯一的规则 R1 写死在 `ncsc/rules.py` 里。#5 需要声明式规则：规则是数据，内核只实现一个通用的匹配与求值器。这一格式必须满足 P-3：前提冲突时不推出结论，且求值必须能终止、结果唯一、不依赖输入顺序。

## 决策

### 1. 文件格式

每条规则一个 JSON 文件，结构由 `schema/rules-0.2.draft.schema.json` 定义：

```json
{
  "format": "ncsc-rules/0.2",
  "id": "resource_unavailable_blocks_task",
  "status": "active",
  "description": "同一分区内，任务需要的资源被确认不可用时，推出任务阻塞。",
  "premises": [
    {"subject": "?task", "relation": "r:task:requires", "object": "?resource", "polarity": "positive"},
    {"subject": "?resource", "relation": "r:resource:unavailable", "object": "c:value:true", "polarity": "positive"}
  ],
  "conclusion": {"subject": "?task", "relation": "r:status:blocked", "object": "c:value:true", "polarity": "positive"}
}
```

| 字段 | 约束 |
|---|---|
| `id` | `[a-z][a-z0-9_]*`，不超过 63 个字符。**语义变化必须换 ID**，因为推导 ID（P-2）由规则 ID 和前提计算，同一 ID 不能对应两种语义 |
| `status` | `proposed`（不执行）、`active`（执行）、`retired`（不执行，保留以便解释历史推导） |
| `premises` | 1–4 条三元组模式，按顺序排列；推导证据的 `premises` 按这个顺序列出断言 ID |
| 项（`subject`/`object`） | 变量 `?name`，或 `c:` 概念常量 |
| `relation` | 必须是 `r:` 常量。不支持关系变量，这样规则就是一阶的，便于按关系建索引 |
| `polarity`（前提） | `positive`：该三元组在本分区的状态必须是“支持”；`negative`：必须是“反对” |
| `polarity`（结论） | 只能是 `positive` |
| 分区 | 不出现在规则中。所有前提与结论隐含共享同一 `(context, valid_at)` |

### 2. 结构层禁止的写法

- 结论为负向。理由：负向证据只能来自原始断言，P-3 的分层求值依赖这一点。
- 前提或结论使用 `r:claim:reported-cause`。理由：报告因果不能作为推理依据，也不能被推出（“报告因果不升级”）。
- 关系位使用变量；未知字段；空前提列表。

### 3. 内核层（加载时）检查

| 检查 | 理由 |
|---|---|
| **安全性**：结论中的每个变量都必须出现在某个前提中 | 否则结论里会有无约束的变量 |
| 常量概念与关系必须已在文档或登记表中声明 | 与 IR 的引用完整性一致 |
| **分层**：负向前提所用的关系，不得是任何 `active` 规则的结论关系 | 见下文“求值语义”第 3 条 |
| 同一组 `active` 规则的 ID 唯一 | |

### 4. 求值语义

在每个分区 `(context, valid_at)` 内独立进行，不跨分区。

1. **基础状态**：只用原始断言，为每个三元组记录正向证据集合与负向证据集合。
2. **前提状态**：
   - 正向前提成立 ⇔ 该三元组有正向证据（原始或推导），且**没有**负向证据；
   - 负向前提成立 ⇔ 该三元组有负向证据，且**没有**正向证据；
   - 有正有负（“冲突”）⇔ 不成立，并在结论查询的 `suppressed` 中记录（P-3）；
   - 无证据（“未知”）⇔ 不成立，也不记录。
3. **不动点**：反复应用所有 `active` 规则，直到本分区不再增加带正负性的事实（主体、关系、客体、极性）。
   - 规则只推出正向结论，所以负向证据集合在求值过程中不会改变，“没有负向证据”是对固定输入的判断。
   - 负向前提要求“没有正向证据”，而正向证据会在求值过程中增加。分层约束（第 3 节）保证负向前提的关系不会被任何规则推出，于是这个判断同样是固定的。
   - 因此，每个前提条件对推导集合都是单调的，不动点唯一。
4. **终止**：声明的概念、关系和极性均有限，分区内每轮只增加事实，故必达事实固定点。证明 ID 不参与该条件。即使事实不变，若递归套用含种子的循环规则，按前提 ID 计算的证明 ID 仍可能持续变化。
5. **同一事实的多条推导**：在事实闭包上按已实例化的规则边构造解释。每条从结论走向原始断言的路径至多访问同一带极性事实一次；到达已在路径中的事实时舍弃该回边。各兄弟前提独立检查路径，允许共享原始叶子。保留所有符合此条件的独立前提组合，按 P-2 以有序前提 ID 计算派生 ID。
6. **链式推导**：前提可以由推导证据满足。其 `d:` ID 对应的子证明须可展开到原始断言（P-5）。查询若超过实现的资源限额须明确失败，不能返回部分解释或以“未知”替代。

### 5. 确定性：证据顺序

查询结果的 `evidence` 与 `suppressed` 都**按 ID 的 Unicode 码位升序排列**（`evidence` 按 `assertion_id`，`suppressed` 按前提 ID 列表）。这样，原始断言（`a:`）总排在推导证据（`d:`）之前，而且结果与输入文档中断言的顺序无关，满足 #5 的验收项“打乱输入仍得到相同证据”。0.1 现行行为是按文档顺序输出，这是 0.2 的输出变化之一。

## 对候选规则（`docs/M0_RULES.md`）的影响

| 候选 | 能否用本格式表达 | 说明 |
|---|---|---|
| R1 必需资源不可用 | 能 | 上面的示例即 R1 |
| R2 前置验收 | 能 | 用负向前提表达“验收 G 明确未通过”：`(?gate, r:gate:passed, c:value:true, negative)`。“尚未验收”没有证据，前提不成立，结论为未知，与候选表的反例一致 |
| R3 最低容量 | 不能 | 需要量值、单位和比较运算；等量值契约另行提出 |
| R4 替换资源 | **不支持，建议撤下** | 要表达“必需资源 R 不可用，但替代品 S 可用，所以不阻塞”，需要“所有替代品都不可用”这样的全称条件。在开放世界假设下，没有记录不等于不可用，这种全称条件无法成立。R1 的录入约束（“需要”只用于必需资源，见标注指南 §2）已经避免了与 R4 的冲突 |
| R5 显式解除 | 暂不能 | 依赖生效时间跨日，需要 P-6 |

## 被否决的备选

- **直接采用 Datalog 文本语法**：表达力相同，但需要另写解析器，错误信息也更难定位到字段。JSON 可以复用同一套 Schema 加内核的两层校验。如果 M3 的规则基线采用 Datalog，可以写一个从 JSON 到 Datalog 的单向转换。
- **允许负向结论**：会让负向证据集合在求值中改变，失去分层保证；规则推出“不阻塞”，在语义上也很容易与“没有证据”混淆。
- **允许否定即失败（“没有记录则……”）**：违反开放世界原则（“缺失不等于否定”）。
