# P-3 规则前提冲突的处理

状态：提议 · 关联 D1 · 语义变化（IR 0.2）

## 问题（D1）

0.1 的 R1 只要求“存在正向前提”。当前提本身在同一分区内有正反证据（查询前提得到“冲突”）时，R1 仍然推出“发布阻塞”，查询结论为“支持”，比证据更确定。

## 判例：三种查询 × 两种方案

按 Codex 在开发方案 §11 中的要求，先列出冲突前提、独立正证据、独立负证据三个场景的预期四值与溯源，再做决定。机器可读版本见 `tests/contract/cases/d1-*.json`，0.1 现状一列已由测试实际验证。

共同数据：`需要`（A+）、`不可用`（B+）同分区；冲突场景另加 `不可用` 的反向断言（B−，来自运维工单）。

| 场景 | 0.1 现状 | 方案 A：不推出 | 方案 B：冲突传播 |
|---|---|---|---|
| ① 仅前提冲突 | 支持（证据：推导） | **未知**，`reason=premise_conflict`，`suppressed` 列出被抑制的推导与对立断言 B− | 冲突 |
| ② 前提冲突 + 直接正证据 | 支持（直接 + 推导） | **支持**（仅直接证据），`suppressed` 同上 | 冲突 |
| ③ 前提冲突 + 直接负证据 | 冲突（直接负 + 推导） | **反对**（仅直接负证据），`suppressed` 同上 | 冲突 |
| 对照：无冲突 | 支持 | 支持，证据带 `trace` | 支持 |
| 对照：冲突在“需要”前提 | 支持 | 未知，`suppressed` 指向 A− | 冲突 |

## 决策：方案 A

规则只有在**每个前提的三元组在本分区查询状态为“支持”**时才触发。前提为“冲突”时不推出结论，而是在结论查询的 `suppressed` 中记录：规则名、前提 ID、哪个前提被哪些对立断言挑战。`suppressed` 只作诊断，不参与四值判定。

## 理由

1. **方案 B 会制造不存在的分歧**。场景①中没有任何来源说“发布未阻塞”，方案 B 却报告“冲突”，等于把“证据对前提有分歧”误报为“证据对结论有分歧”。场景②更糟：一条独立、无争议的直接证据被无关前提的分歧降级。
2. **方案 A 保持四值的含义不变**：结论的状态只由“可接受的证据”决定；“为什么没推出”由 `suppressed` 说明，信息不丢失。
3. **可分层、可终止**。规则只推出正向结论（P-4 将把这一条写成约束），负向证据只来自原始断言。因此“前提无负向证据”是对固定输入的静态判断，“前提有正向证据”对推导结果单调；先算负向集合，再对正向做不动点求值，结果唯一且必然终止。这为 #5 的链式推导提供了无需复杂非单调逻辑的实现路径。
4. 与“未知不等于否定”一致：场景①返回未知而不是反对。

## 代价与风险

- 推导从单调变为“对负向证据非单调”：新增一条反向断言可能撤回推导。这是有意为之，并通过 `suppressed` 可见。
- 前提的“支持”可能来自其他推导（链式）。实现时前提状态必须在同一不动点中计算，不能只看原始断言；#5 需要两跳判例覆盖。
