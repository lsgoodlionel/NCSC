# IR 0.1 → 0.2 迁移清单

状态：提议 · 关联 #3（契约）、#4（校验器与迁移工具实现）

迁移工具（`ncsc migrate`，#4 实现）必须是纯函数：输入 0.1 文档，输出 0.2 文档与迁移报告；不能自动确定的项进入 `needs_confirmation`，**不得猜测**。参考输出见 `tests/contract/migration/0.1-to-0.2/`。

**候选与正式输出**：只要报告的 `needs_confirmation` 非空，工具输出的 0.2 文档就只是**候选文档**（报告中 `output_status: "candidate"`），其中待确认项填的是建议值。候选文档不得作为正式数据写入数据集或注册表；只有每一项都得到显式确认（例如以确认文件作为工具的第二个输入），且重新运行后 `needs_confirmation` 为空，输出才是正式文档（`output_status: "final"`）。参考输出中“任务 → event”就是这种建议值，所以它是候选文档。

## 1. 破坏性变化

| # | 变化 | 来源 | 0.1 数据受影响的情况 | 迁移方式 |
|---|---|---|---|---|
| B1 | `version` 改为 `"0.2"` | — | 全部 | 自动 |
| B2 | `kind` 改为 6 值枚举 | P-1 | 全部概念 | 按映射表自动；表外或有歧义的进入人工确认 |
| B3 | `r:` 前缀 ⇔ `kind=relation` | P-1/P-2 | 关系概念未用 `r:`，或非关系概念用了 `r:` | 人工确认（涉及改 ID） |
| B4 | `relation` 位只接受 `r:`，主语/宾语只接受 `c:` | P-1（D3） | 违反者 | 拒绝并报告，不自动改 |
| B5 | ID 语法：小写、无空白、单行、指定前缀 | P-2（D5） | 不合语法的 ID | 只做无歧义的规范化（去首尾空白）；其余进入人工确认。**若规范化后与已有 ID 或另一条规范化结果同名，两者都不改，进入人工确认**（否则会把两个概念静默合并） |
| B6 | `context` 必须为 `ctx:` ID | P-2 | 自由文本上下文 | 人工确认（需要给上下文命名） |
| B7 | 来源 ID 必须为 `src:` ID；同一断言内不重复 | P-2 | 违反者 | 重复项：内容相同则自动去重，不同则人工确认 |
| B8 | 别名与来源说明：概念内唯一、去首尾空白、单行、至少一个别名含汉字 | P-7 | 违反者 | 去重与去首尾空白自动；含内部换行的、缺汉字别名的进入人工确认 |
| B9 | `valid_at` 零填充 | D2 | 无：0.1 内核自 #12 起已拒绝 `2026-1-5` 类日期，合法 0.1 文档不会含此类值 | 不需要迁移 |
| B10 | 推导规则：前提冲突时不推出 | P-3（D1） | 依赖 0.1 推导结果的下游 | 无数据迁移；行为变化写入发布说明 |
| B11 | 查询未声明 ID 报错 | P-5（D4） | 依赖“拼错返回未知”的调用方 | 无数据迁移；行为变化写入发布说明 |
| B12 | 推导 ID 格式改为 `d:<rule>:<hash>` | P-2（D8） | 保存过 0.1 推导 ID 的下游 | 无数据迁移；0.1 推导 ID 不是持久标识，不提供映射 |

增量（非破坏）：`status_code`、`trace`、`suppressed`、`reason`、`other_partitions`。

## 2. `kind` 映射表

| 0.1 `kind` | 0.2 `kind` | 是否需确认 |
|---|---|---|
| 关系 | relation | 否 |
| 资源 | entity | 否 |
| 值 | value | 否 |
| 任务 | event | **是**：可视为计划中的活动（event）或被管理的工作项（entity） |
| 其他任何文本 | — | **是** |

## 3. 身份迁移

本节回答“数字身份”如何过渡。0.1 示例使用可读 ID；NCSC V1.0 原文设想过以十类数字编码概念身份。0.2 的规则：

1. **身份与编码分离**。任何数字或分类编码（包括十类前缀，如 `1.03.0007`）都不得作为概念身份或参与语义计算。若已有此类编码，迁移时为每个编码分配新的不透明 ID，原编码只作为注册表中的历史引用保存，不进入 IR 0.2。
2. **可读 ID 的去留**。0.1 示例中的 `c:task:release` 等可读 ID 符合 0.2 语法，迁移工具**不改写**，避免无谓的身份变更。新增的生产数据应使用不透明 ID（P-2）。是否在正式数据集（#6）冻结前把示例换成不透明 ID，留给数据负责人决定。
3. **永不复用**。ID 一经发布，即使概念被删除也不再分配给其他概念。
4. **合并与拆分**属于注册表能力，不在 IR 0.2 中表达：合并时旧 ID 标记废弃并重定向到新 ID，历史断言不改写；拆分时旧 ID 指向多个后继，引用旧 ID 的断言必须逐条人工重判，不得自动挑选。注册表的数据结构在 M2 之后单独提案。

## 4. 人工确认项汇总

迁移报告的 `needs_confirmation` 至少覆盖：

- `kind` 为“任务”或映射表以外的文本；
- 需要改 ID 的情况（B3、B5 中不能只靠去空白解决的部分），以及规范化后发生同名碰撞的 ID；
- 自由文本上下文的命名（B6）；
- 同一断言内同 ID、不同说明的来源（B7）；
- 含内部换行的别名或来源说明、没有任何含汉字别名的概念（B8）。

每项给出 JSON 路径、原值、建议值（如有）、备选值和原因。报告中 `rejected` 列出 B4 这类无法迁移、必须由数据负责人修正源数据的项。

### 报告字段

| 字段 | 含义 |
|---|---|
| `output_status` | `final`：无待确认项且候选通过 0.2 校验；否则为 `candidate` |
| `automatic` | 已自动完成的变换 |
| `needs_confirmation` | 待人工确认的项（本节所列） |
| `id_changes` | ID 改写（B3、B5），每项含旧 ID、新 ID 与依据 |
| `rejected` | B4 这类必须回到源数据修正的项 |
| `unhandled_first_error` | 预览尚未覆盖的不兼容项：候选文档 0.2 校验的**首个**错误，且不属于任何待确认项。出现时 CLI 退出码为 2。B3、B5–B8 全部实现后，应改为完整的错误列表 |

CLI 退出码：0 为 `final`；1 为 `candidate`，需要确认；2 为输入无效、存在 `rejected` 或 `unhandled_first_error`。

## 5. 验收

- `tests/contract/migration/0.1-to-0.2/project_state.0.2.json` 通过 0.2 结构层 Schema（已由 `fixtures/0.2/valid/example-migrated.json` 覆盖，两者内容相同）。

- 提供“任务 = event”的确认后，`needs_confirmation` 为空，`output_status` 为 `final`，文档内容不变。
