# P-6 时间区间

状态：提议 · 关联 #6（“P-6 单独评审”）、候选规则 R5 · 新增字段，IR 版本升为 0.3

## 问题

IR 0.1/0.2 只有单日 `valid_at`。数据集 `datasets/synthetic-v0/needs-p6.md` 记录了两类无法如实表达的句子：

- “11月19日**起**构建配置要求发布使用签名密钥”：只能标成 19 日单日，查询 20 日得到“未知”；
- “签名密钥 18 日不可用，19 日**恢复**可用”：19 日之后的状态无法表达。

候选规则 R5（显式解除）也依赖“生效之后持续有效”。

## 决策

### 1. 数据：新增 `valid_during`

```json
{"valid_during": {"from": "2026-11-19"}}
{"valid_during": {"from": "2026-11-18", "to": "2026-11-20"}}
{"valid_during": {"to": "2026-11-21"}}
```

- **闭区间，以日为单位**，两端都包含当日。
- `from` 缺省表示起点未给出，`to` 缺省表示终点未给出；至少给出一端。
- `valid_at` 与 `valid_during` **不能同时出现**。单日仍然用 `valid_at`；`{"from": D, "to": D}` 与 `valid_at: D` 语义相同，但标注时应写成 `valid_at`。
- 由内核检查：`from` 不晚于 `to`、日期在日历上有效。
- 不支持小时、时区和模糊时间（“月底前后”）。

### 2. 查询：仍按单日

查询参数仍是单个 `valid_at`（或不给，表示无日期分区）。某条断言在查询日 D **可用**，当且仅当：

| 断言的时间 | 在 D 可用的条件 |
|---|---|
| `valid_at: X` | X = D |
| `valid_during: {from, to}` | (`from` 缺省或 `from` ≤ D) 且 (`to` 缺省或 D ≤ `to`) |
| 无日期 | 仅当查询也不给日期 |

**无日期不等于“一直有效”**：无日期断言只属于无日期分区，不参与任何具体日期的查询；具体日期的断言也不参与无日期查询。这与 0.2 完全相同。

### 3. 规则：在“当日视图”中求值

查询日 D 的分区，就是在 D 可用的全部原始断言。P-3 的冲突判定、P-4 的分层不动点都在这个分区内原样进行，不需要修改。

- 推导证据增加 `valid_during`，取各前提时间范围的**交集**（单日前提视为 `[X, X]`）。只有当至少一个前提带区间时才给出；全是单日前提时，交集就是查询日本身，不重复给出。
- 推导 ID 仍是 `d:<rule>:<hash>`（P-2），只由规则和前提决定，与查询日无关。同一组前提在不同日期推出的是同一条推导。

### 4. 输出

- 原始断言带区间时，证据中原样给出 `valid_during`。
- `other_partitions`（P-5）的条目可以用 `valid_during` 代替 `valid_at`。为避免计算开放区间上的全部推导，**`other_partitions` 只统计原始断言**，不统计推导证据。这一条同时是对 P-5 的澄清。

### 5. 版本

新增字段使用封闭字段集的 Schema，因此 IR 版本升为 **0.3**（`schema/ir-0.3.draft.schema.json`）。0.2 文档只需把 `version` 改为 `"0.3"` 即可通过 0.3 校验，没有其他迁移项。

## 理由

- **查询仍按单日**，保持了“分区精确匹配”的简单性：每次查询的证据集合是确定的，四值判定、冲突、规则求值都无需改变。区间只改变“断言属于哪些分区”。
- **交集**是唯一不会过度推论的选择：结论只在所有前提都成立的日期成立。
- **开放区间**如实反映“起”“截至”这类说法：来源本身没有给出终点。风险是结论在很远的日期仍然成立；对策是证据中明确给出 `valid_during`，使用者能看到这是一条开放区间。
- 拒绝“无日期 = 一直有效”，与开放世界原则一致：没有日期的记录，不能被解读成对每一天都作了陈述。

## 被否决的备选

- **查询也用区间（“19–21 日期间是否阻塞”）**：需要定义区间上的四值聚合（部分日期支持、部分未知时怎么判？），复杂度高、用例不足。需要时可以由调用方逐日查询。
- **把开放区间截断到“已知最后日期”**：要引入“数据集当前日期”这一全局状态，并使结果依赖查询时刻，破坏确定性。
- **区间端点用时间戳**：现有数据和用例都以日为单位；引入时区会带来新的歧义。

## 不在本提案范围

- **记录时间 / 获知时间**（`docs/v0.1` 的双时间）：另行提出。
- **事件时间与持续时长**（“会议持续两小时”）：需要量值契约。

## 判例

| 文件 | 内容 |
|---|---|
| `fixtures/0.3/valid/*` | 单日不变、闭区间、开放终点、开放起点 |
| `fixtures/0.3/structural/*` | 单日与区间并存、空区间、未知字段、非零填充端点、端点含换行 |
| `fixtures/0.3/value/*` | 起点晚于终点、日历无效（结构层通过，内核拒绝） |
| `cases/p6-open-interval-rule.json` | 开放区间前提与单日前提：仅 20 日触发，结论 `valid_during` 为 `[20, 20]` |
| `cases/p6-recovery.json` | “18 日不可用，19 日起恢复”：18 日支持，19 日及以后反对，17 日未知并给出 `other_partitions` |
| `cases/p6-overlap-conflict.json` | 两个区间只在 20 日重叠：只有 20 日冲突 |
| `cases/p6-undated-not-always.json` | 无日期断言不参与 19 日查询 |

内核侧全部标为 `unimplemented:P-6`。判例的期望结果已通过查询结果 Schema 校验。
