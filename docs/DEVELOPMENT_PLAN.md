# NCSC 开发方案（完善版）

> 基线：`94e853d feat: add deterministic NCSC prototype`，评估日期 2026-11-19。
> 本文在 `README.md` 与 `CLAUDE_HANDOFF.md` 的基础上，补充现状评估、经实测确认的缺陷、分阶段路线图、验收标准与风险。
> 凡涉及共享契约（IR version、四值状态词、作用域语义、来源/溯源字段）的条目均为**提案**，须按 `CLAUDE_HANDOFF.md` 的评审流程通过后才能落地。
> 本文不预填任何性能或准确率数字。

## 1. 现状评估

### 1.1 已有能力

| 模块 | 文件 | 能力 |
|---|---|---|
| IR 校验 | `ncsc/core.py::validate_document` | 封闭字段集、重复 ID、悬空引用、非空来源、单日 `valid_at` |
| 规则推理 | `KnowledgeBase._apply_whitelist_rules` | 1 条硬编码规则 `resource_unavailable_blocks_task`，带前提溯源 |
| 四值查询 | `KnowledgeBase.query` | 支持 / 反对 / 冲突 / 未知；按 `(context, valid_at)` 精确分区 |
| CLI | `ncsc/cli.py` | `validate`、`query`，错误时 exit 2 |
| 测试 | `tests/test_core.py` | 9 个用例，全部通过（Python 3.15.2，Windows） |

### 1.2 设计上的优点（应保留）

- **缺失 ≠ 否定**：开放世界假设，未知就是未知。
- **报告因果不升级**：`r:claim:reported-cause` 只是记录，不参与推理。
- **严格拒绝**：未知字段、悬空引用直接报错，不做猜测。
- **零外部依赖**：纯标准库，离线、确定性。

### 1.3 主要短板

- 规则硬编码在内核里，无法扩展，也没有注册表、优先级、循环检测。
- 没有类型系统：`kind` 只是自由文本，角色位置不检查概念类别。
- 没有工程化外壳：无 `pyproject.toml`、无 CI、无 lint/类型检查，README 命令用 `python3`（Windows 默认环境下指向应用商店占位符）。
- 契约只存在于 Python 代码和 README 文字中，没有机器可读的 Schema。

## 2. 实测确认的缺陷

以下问题均已用脚本复现（复现方式见每条“复现”）。按严重度排序。

### D1【高】前提冲突时规则仍推出“支持”

- **现象**：同一分区内对 `签名密钥 不可用=true` 同时有正、反断言（查询该前提得到“冲突”），但规则只看正向前提，仍推出 `发布任务 阻塞=true`，查询结果为“支持”。
- **影响**：违反“冲突应传播而非被掩盖”的直觉，结论比证据更确定。
- **建议**：规则前提必须在同一分区内是“支持”状态才触发；若前提为“冲突”，结论也应带冲突标记或不推出。具体语义属于共享契约，需提案评审（见 §5 P-3）。

### D2【中】日期格式校验过松，导致静默“未知”

- **现象**：`strptime("%Y-%m-%d")` 接受 `2026-1-5`；数据写 `2026-1-5`，查询 `2026-01-05` 匹配不上，返回“未知”且无任何提示。
- **建议**：用正则 `^\d{4}-\d{2}-\d{2}$` + `date.fromisoformat` 严格校验，或在加载时规范化为零填充格式。属正确性修复，不改变契约语义。

### D3【中】角色位置不检查概念类别

- **现象**：把 `c:task:release` 填在 `relation` 位置可通过校验。
- **建议**：IR 0.2 引入受控 `kind` 枚举（至少区分“关系”与“非关系”），`relation` 位只能引用关系概念（提案 P-1）。

### D4【中】查询未声明的概念 ID 返回“未知”而非报错

- **现象**：`c:task:relase`（拼写错误）查询得到“未知”，与“真的没有证据”无法区分。
- **建议**：查询时校验 subject/relation/object 均为已声明 ID，未声明则报错；可提供 `--allow-undeclared` 显式放宽。

### D5【低】ID 前后空白未规范化

- **现象**：`" c:task:release"` 与 `"c:task:release"` 被视为两个不同概念同时存在。
- **建议**：ID 规定匹配 `^[a-z]+(:[a-z0-9-]+)+$` 一类的正则（具体格式提案 P-2），非法即拒绝。

### D6【低】别名跨概念冲突不检测

- **现象**：两个概念都可声明别名“发布任务”。
- **建议**：同一 `kind` 内别名唯一，或至少给出警告；为未来中文词面解析预留确定性。

### D7【低】CLI 读到非 UTF-8 文件时抛出原始堆栈

- **现象**：`UnicodeDecodeError` 不在 `except` 列表中，打印 traceback 而不是结构化 JSON 错误。
- **建议**：捕获 `UnicodeDecodeError`（或统一捕获 `ValueError`），保持 exit 2 + JSON 错误输出。

### D8【低】推导 ID 拼接可能碰撞、来源未去重

- **现象**：推导 ID 为 `derived:{A}+{B}`，若断言 ID 本身含 `+` 可构造碰撞；派生断言的 `sources` 直接拼接，多条规则链式推导后会重复。
- **建议**：推导 ID 改为 `derived:{rule_id}:{sha1(sorted premises)}` 之类的规范形式；来源按 ID 去重。和规则注册表一起做。

### 测试缺口

- `test_reported_cause_does_not_infer_verified_fact` 只剩一条断言，即使规则错误地使用了报告因果也会得到“未知”，**断言力度不足**。应构造“报告因果 + 资源需要”但无“不可用”的场景。
- 没有 CLI 测试（退出码、stderr JSON 格式）。
- 没有“无 `valid_at` 数据 + 有 `valid_at` 查询”的混合分区测试。

## 3. 目标与非目标

### 3.1 一年内目标

1. 一个**有正式 Schema、可扩展规则、可审计溯源**的确定性语义内核。
2. 一套**人工标注的小型基准数据集**，以及与 JSON 精确匹配 / 轻量 KG / 通用规则引擎的**可复现对比**。
3. 一个**模型适配层**：LLM 只能产出候选 IR，必须经过同一校验器和内核，不能绕过。
4. 有测量方法的非功能评估（规模、延迟、内存、可重复性）。

### 3.2 明确非目标（至少到 M4 之前）

- 不做概率推理、置信度融合。
- 不做开放世界规则学习。
- 不把“0–9 十类”作为公理；它只能作为待验证假设进入 M3 的实验设计。
- 不在内核中做自然语言解析；中文词面只经由别名表做确定性映射。

## 4. 目标架构

```
             ┌──────────────┐
 自然语言 ──▶ │ adapters/    │ ── 候选 IR ──┐       （M4，可选，离线可关闭）
             └──────────────┘              │
                                           ▼
 JSON IR ───────────────────────▶ ┌───────────────────┐
                                  │ schema/ (JSON     │  单一契约来源
                                  │ Schema 0.x)       │
                                  └─────────┬─────────┘
                                            ▼
                                  ┌───────────────────┐
                                  │ ncsc/validate.py  │  Schema + 语义校验
                                  └─────────┬─────────┘   (引用、类别、ID 格式)
                                            ▼
                                  ┌───────────────────┐
                                  │ ncsc/store.py     │  按 (context, valid_at)
                                  │                   │  分区索引
                                  └─────────┬─────────┘
                                            ▼
                 rules/*.json ──▶ ┌───────────────────┐
                                  │ ncsc/rules.py     │  注册表、不动点求值、
                                  │                   │  循环检测、推导去重
                                  └─────────┬─────────┘
                                            ▼
                                  ┌───────────────────┐
                                  │ ncsc/query.py     │  四值查询 + 溯源树
                                  └─────────┬─────────┘
                                            ▼
                                  cli.py / Python API / baselines/
```

拆分原则：

- `core.py` 保留为对外兼容的门面（`KnowledgeBase`、`IRValidationError`），内部委托给新模块，避免破坏现有调用方。
- 规则从代码变为**数据**（声明式模式：前提三元组模板 + 结论模板 + 变量绑定），内核只实现一个通用匹配器。现有硬编码规则成为第一条声明式规则，用回归测试锁定行为一致。
- 分区索引 `(context, valid_at) → {(s, r, o) → [assertion]}`，让查询从 O(N) 扫描变为 O(1) 查找，并为规模测试做准备。

## 5. 契约变更提案（IR 0.2 草案）

每条需形成独立提案文件 `docs/proposals/P-x.md`，由接口负责人 + 内核负责人评审。

| 编号 | 内容 | 动机 | 兼容性 |
|---|---|---|---|
| P-1 | `kind` 改为受控枚举（如 `entity`/`relation`/`value`/`task`/`resource`…，中文显示名另设）；`roles.relation` 必须指向 `relation` 类 | D3 | 破坏性，升 0.2 |
| P-2 | 概念/断言/来源/上下文 ID 格式正则 | D5、D8 | 破坏性，升 0.2 |
| P-3 | 规则前提冲突的传播语义：前提“冲突”时结论为“冲突”或不推出（二选一，需论证） | D1 | 语义变化，升 0.2 |
| P-4 | 规则声明格式（`rules/*.json`）：`id`、`version`、`premises`（含极性要求）、`conclusion`、`description` | 可扩展性 | 新增，不破坏 0.1 数据 |
| P-5 | 查询响应增加 `trace` 树（递归展开推导前提），并给出 `reason` 字段区分“无证据”与“概念未声明” | D4、可审计性 | 响应扩展 |
| P-6 | 时间：在单日之外支持闭区间 `{"from","to"}`，查询按“区间包含”匹配 | README 已列边界 | 新增，需单独评审，排在 M3 |
| P-7 | 别名唯一性范围与中文别名策略（是否强制含 CJK 字符） | D6 | 校验加严 |

0.1 → 0.2 迁移：提供 `ncsc migrate` 子命令，把 0.1 文档转换为 0.2，无法自动推断的（如 `kind` 映射）输出待人工确认清单，不静默猜测。

## 6. 路线图

每个里程碑都以“验收命令全部通过 + 新增测试覆盖 + 文档更新”为完成标准。时间估计以 1 名全职开发者计，仅供排期参考。

| README 命令改为 `python -m …`，并说明 Windows 的 `python3` 问题 | README | 新机器按 README 可跑通 |

### M2 规则引擎（约 2–3 周）

| 任务 | 产出 | 验收 |

### M3 数据、标注与基线（约 3–4 周）

| 任务 | 产出 | 验收 |
|---|---|---|
| 人工标注指南：概念、关系、极性、上下文、时间、**报告因果 vs 验证因果** | `annotation/GUIDE.md` | 两名标注者试标，记录分歧类别 |
| 小型可审计数据集（合成或公开可用材料，不含敏感信息），带问答对与期望四值答案 | `datasets/` | 每条都能追溯到来源说明 |
| 标注一致性测量（如 Cohen's κ），方法先冻结再测 | `annotation/agreement.md` | 只报告实测值 |
| 三种基线：JSON 精确匹配、轻量 KG（内存三元组 + SPARQL 式模式匹配）、通用规则引擎（如 Datalog 实现） | `baselines/` | 同一数据集、同一评分脚本可复现 |
| 评测脚本：四值准确率、混淆矩阵（尤其“未知”被误判为“反对”的比例）、溯源完整率 | `eval/` | 一条命令产出报告 |
| P-6 时间区间（若评审通过） | 内核 + 测试 | 区间包含语义测试 |
| “0–9 十类”假设的可证伪实验设计（只设计，不预设结论） | `docs/experiments/ten-classes.md` | 写明假设、对照、判定标准 |

### M4 模型适配层（约 2–3 周，可选）

| 任务 | 产出 | 验收 |
|---|---|---|
| 适配器接口：`propose_ir(text, schema) -> candidate_doc` | `adapters/base.py` | 无网络时可整体关闭，内核测试不受影响 |
| 一个参考实现（任选模型提供方），通过环境变量读密钥，默认不启用 | `adapters/` | 密钥缺失时给出清晰提示，不影响离线功能 |
| 候选 IR 必经同一 `validate_document`；失败不重试猜测，原样报告 | 测试 | 构造非法候选被拒 |
| 抽取质量评测：在 M3 数据集上测 IR 抽取的精确率/召回率 | `eval/` | 只报告实测值 |

### M5 非功能验证（约 2 周）

先写测量方法（硬件、数据规模梯度、重复次数、统计口径），冻结后再测：

- 规模：断言数 10³ / 10⁴ / 10⁵ / 10⁶ 下的加载、推导、查询耗时与峰值内存；
- 可重复性：相同输入多次运行结果逐字节一致；
- 错误诊断：每类拒绝的错误信息是否能定位到具体字段路径；
- 安全边界：超大文件、深嵌套、超长字符串的资源上限（加载前限制文件大小与数量）。

## 7. 质量策略

- **测试分层**：单元（校验/规则/查询）→ 契约（Schema 与 Python 一致性）→ CLI 端到端 → 属性测试（顺序无关、确定性）→ 回归（每个修复的缺陷 D1–D8 各留一个测试，命名 `test_regression_dN_*`）。
- **覆盖率**：引入 `coverage`，对 `ncsc/` 设置分支覆盖门槛（门槛值在 M0 实测当前覆盖率后再定，不预设）。
- **确定性**：所有输出中的列表显式排序；禁止依赖 dict/set 迭代顺序表达语义。
- **零依赖承诺**：运行时只用标准库；开发依赖（ruff、mypy、jsonschema、coverage）放在 `[project.optional-dependencies].dev`。
- **版本**：IR 版本与包版本分开管理；IR 任何破坏性变化都升 minor（0.1 → 0.2）并提供迁移工具。

## 9. 风险与对策

| 风险 | 可能性 | 影响 | 对策 |
|---|---|---|---|
| 严格拒绝策略让真实数据难以接入 | 高 | 中 | 迁移工具输出待确认清单；提供 `validate --report` 一次列出全部错误，而非遇到第一个就停 |
| 规则语义（尤其冲突传播）争议拖慢 M2 | 中 | 高 | P-3 先在 M1 评审；评审期间规则引擎按可配置策略实现，默认保守（不推出） |
| 精确分区导致大量“未知”，用户误以为系统失效 | 高 | 中 | 查询响应给出 `reason`（无证据 / 概念未声明 / 只在其他分区有证据），提示但不合并 |
| 模型适配层被当作事实来源 | 中 | 高 | 候选 IR 的来源强制标注为模型生成；默认关闭；评测分开报告 |
| “0–9 十类”假设未经验证就渗透进设计 | 中 | 中 | 只允许出现在 `docs/experiments/`，内核代码不引用 |
| 文档中出现未测指标 | 中 | 中 | Review 检查项：所有数字必须链接到 `eval/` 中的产出文件 |
